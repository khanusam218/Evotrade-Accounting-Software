End-to-end test plan · Evotrade Accounting Software

One business, entered start to finish, with the numbers worked out in advance.

This is a single continuous story: a real business, opened fresh, trading for its first month. Every module gets exercised in the order a business would actually hit it, with the exact figures to type in and the exact result the system should show back. Where the code does something a normal person wouldn't expect, that's called out before you get there — so a surprising number means "known behaviour," and a wrong number means "actual bug."

How to use this

Work through the sections in order — later modules assume earlier ones already exist (the Sales Invoice needs the Customer and Product to already be saved, the Receive Payment needs the Invoice, and so on). Each step gives you a table of exactly what to type, then one of four callout types:

Calc — the arithmetic the system should run, shown so you can check it by hand.  Watch — non-obvious real behaviour: not a bug, just easy to misread as one.  Bug — a genuine defect found while researching this plan; the expected result documents what it actually does today.  Fixed — a defect that was fixed as part of this same work session; flagged so you can confirm the fix actually took.

All figures are in PKR. Dates below say "today" / "today+N days" — substitute the actual date you run the test on.

Fixed this session

Every module below that posts automatically to Accounts Receivable / Accounts Payable / Undeposited Funds (Sales Invoices, Receive Payments, Purchase Invoices, Returns, Refunds, Settlements, Credit/Debit Notes, Bank Deposits) used to write to an old, hidden, deactivated copy of these accounts because of a naming mismatch — so postings were invisible unless you ticked "Show Inactive." Known bug — not fixed

This is a report-side gap, not something your data entry can fix.

Appendix B — validation changes made this session

Every form in the system was audited. In addition to the specific fixes flagged inline above, the general pattern applied everywhere: a "name"-type field must now contain at least one letter (blank, whitespace-only, purely numeric, or symbols-only text is rejected before save); percentage fields are capped 0–100; money/quantity fields that should never be negative now reject negative input; required fields that only looked required (an asterisk with no actual check behind it) now genuinely block save with an inline message. This touched every Sales, Purchase, Accounts, Inventory/Manufacturing, and CRM/HR/POS/Setup form in the app — if you hit a field anywhere in this plan that rejects bad input with a message, that's this change working as intended.
